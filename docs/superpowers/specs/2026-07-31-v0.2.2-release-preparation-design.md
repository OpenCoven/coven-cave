# v0.2.2 Release Preparation Design

## Goal

Prepare one reviewable release-stamp pull request for CovenCave v0.2.2 from
commit `330fc19b2a7b998019dadb0ef0c2f170b866ff6d` (`origin/main` through PR
#4113). The pull request must be ready for protected-branch review, but this
work does not merge the pull request, create or push the v0.2.2 tag, dispatch
the release workflow, or upload release artifacts.

## Release Boundary

The release contains the 101 non-merge commits after v0.2.1 through the approved
cut. If `main` advances before the release pull request merges, the release
owner must explicitly choose whether to keep this boundary or refresh the
changelog and branch to include the newer commits. The tag must never include
changes omitted from the v0.2.2 changelog.

## Version Stamp

Set the shipped marketing version to `0.2.2` in all five version-bearing
surfaces:

1. `package.json`
2. `src-tauri/tauri.conf.json`
3. `src-tauri/Cargo.toml`
4. The `app` package block in `src-tauri/Cargo.lock`
5. `apps/ios/CovenCave/project.yml`

The iOS `CURRENT_PROJECT_VERSION` remains `1`; TestFlight preparation and build
number advancement are outside this pull request.

Add a dated `0.2.2` section directly below `Unreleased`. Replace the generated

The changelog should cite the principal pull requests without reproducing all
101 commit subjects.

## Release Tooling Correction

`scripts/release-yaml-settings.mjs` is the shared semantic YAML helper used by
both `scripts/stamp-release.mjs` and `src/lib/app-version.test.ts`. It enforces
the canonical XcodeGen path `settings.base.MARKETING_VERSION`, preserves the
source scalar's plain or quoted formatting when stamping, and fails closed on
noncanonical, duplicate, aliased, multiline, malformed, or complex-key input.
`apps/ios/CovenCave/project.yml` remains one of the five `STAMP_FILES`.

Update the helper tests to prove:

- exactly five version surfaces are stamped;
- only the canonical iOS `settings.base.MARKETING_VERSION` changes;
- scalar source formatting is preserved;
- noncanonical, duplicate, aliased, and complex inputs are rejected;
- `CURRENT_PROJECT_VERSION` remains unchanged; and
- unrelated matching versions are not rewritten.

Use the same semantic reader in `src/lib/app-version.test.ts` and require the
iOS marketing version to equal `package.json.version`. This turns the
five-location release contract into an enforced invariant.

## Validation

Run the smallest release-focused gates first:

- release-stamp helper tests;
- app-version consistency test;
- release-notes tests;
- release runtime and macOS signing contract tests;
- test-wiring check; and
- `git diff --check`.

Then run the repository typecheck and the existing pull-request checks. The
release pull request body records the exact approved base commit, the five
version changes, the curated changelog boundary, and all validation evidence.

## Publication Gates

The release pull request may be opened while publication prerequisites are
pending, but it must state that tagging is blocked. The v0.2.2 tag and release
workflow must not run until:

1. `@opencoven/cli@latest` is at least `0.2.2`;
2. the release pull request is merged through protected `main`;
3. every required pull-request check is green;
4. the final release commit and changelog boundary are reconciled; and
5. the signed tag is created from the intended merged commit.

At design time, npm reports `@opencoven/cli@latest` as `0.2.1` and
`@opencoven/cli@0.2.2` as missing.

## Failure Handling

Abort preparation if another release-stamp pull request appears, the release
branch or remote tip changes unexpectedly, any version surface cannot be
updated exactly once, or the approved cut cannot be reproduced. Do not tag,
dispatch a release, or use recovery workflow overrides as part of this task.
