# `bin/coven-autoloop` — v0.2 CLI wrapper scoping spec

**Status:** scoping handoff, not yet built. Written by Sage 2026-08-18 for Cody
to implement. This closes the "v0.2 (planned)" line in
`~/.coven/skills/coven-autoloop/SKILL.md`'s Ship state section: *"`bin/coven-autoloop`
shell wrapper that enforces atomicity of steps 4/5/7. Depends on Cody scoping."*

Do not confuse this with the read path already shipped in
`src/lib/research-autoloop.ts` / `src/lib/server/research-autoloop.ts` (parses
the ledger/events for the Cave UI). This spec is the **write path**: a CLI
Sage (or any familiar running the skill) invokes once per iteration to make
steps 4, 5, and 7 of the contract atomic instead of three unrelated manual
edits.

## Why this exists

Per the skill's own incident note: between iter 82 (2026-07-18) and the
skill landing (2026-07-26), five synthesis notes were written and **zero**
TSV rows were appended — the ledger step was manual and optional, so it got
skipped under context pressure. A CLI wrapper that either fully succeeds or
visibly fails removes the "forgot to run the last step" failure mode.

## Contract this CLI must enforce

Steps 4/5/7 from the skill (verbatim numbering preserved for cross-reference):

1. **Step 4 — append TSV row.** All-or-nothing: either the full 10-field row
   lands or nothing does. No partial-row writes on crash mid-append.
2. **Step 5 — regenerate index.** Best-effort: run the Python script; if it
   fails, the iter is **not** aborted (steps 4 and 7 already succeeded) but
   the CLI must print/log a visible `index-stale` warning and exit non-zero
   so the caller (Sage) notices and can retry step 5 alone later.
3. **Step 7 — emit completion event.** Only runs after step 4 succeeds.
   Appends one line to `logs/autoloop.jsonl`; creates the file (and its
   parent `~/.coven/logs/` dir) if missing.

Everything else (source verification, synthesis writing, self-scoring,
skill-pack staging) stays manual/agent-driven — this CLI only owns the
receipt mechanics, per the skill's explicit scope.

## Proposed interface

```
bin/coven-autoloop record \
  --kind synthesis \
  --slug identity-preservation-agents \
  --score 27 \
  --verdict ACCEPT \
  --branch main \
  --summary "One-paragraph summary matching the synthesis opening thesis." \
  --synthesis research/synthesis/identity-preservation-agents-2026-08-18.md \
  [--staged-skill research/skills/identity-preservation-agents/] \
  [--inbox-delta 0] \
  [--score-delta +2]
```

- `iter` is **not** a flag — the CLI computes `max(existing iter) + 1` itself
  under a lock (see below), so callers can't race or hardcode a stale value.
- `timestamp` is not a flag — CLI stamps `new Date().toISOString()` (or
  equivalent) at write time.
- Reject (exit 2, no writes) on: unknown `--verdict`, `--score` outside
  0–30, missing required fields, `--synthesis` path that doesn't exist or
  resolves outside `~/.coven/research/synthesis/`, `--staged-skill` path
  that doesn't exist or resolves outside `~/.coven/research/skills/`.
- A dry-run flag (`--dry-run`) that validates and prints the row/event
  without writing is worth adding — cheap and useful for the calling agent
  to sanity-check before committing.

## Atomicity mechanics (the actual scoping question for Cody)

1. **Locking:** take an exclusive lock on a sibling lockfile (e.g.
   `results.tsv.lock` via `flock`/`proper-lockfile`, following the pattern in
   `worktree-autolock.mjs`) before reading current max `iter` and before
   appending — otherwise two concurrent `record` calls (e.g. two familiars
   running the skill at once) can compute the same `iter` or interleave
   writes mid-line.
2. **Compute iter:** read the ledger, parse field 3 of every row, take
   `max + 1`. Do this inside the lock, not before it.
3. **Append TSV row:** write to a temp file in the same directory, then
   `fsync` + append (or lock-protected direct append) — the goal is "no
   half-written line," not full filesystem transactionality; a lock plus a
   single buffered `write()` of the whole line (ending in `\n`) is
   sufficient in practice since POSIX guarantees atomicity for writes under
   `PIPE_BUF`/`O_APPEND` for reasonably short lines. Cody should pick
   whichever of these is simplest to test reliably rather than over-engineer.
4. **Release lock**, then run step 5 (index regen) **outside** the TSV lock
   — it's read-only relative to the ledger and shouldn't block the next
   `record` call.
5. **Step 7** runs regardless of step 5's outcome, appending to
   `logs/autoloop.jsonl` (create dir/file if absent). This file has no
   documented locking requirement in the skill and is append-only, so a
   simple `O_APPEND` write is adequate; add a lock only if testing reveals
   interleaving under real concurrency.

## Testing

Follow the repo's existing `.test.mjs`/`.test.ts` pairing convention (see
`worktree-autolock.test.mjs`, `beads-jsonl-merge-driver.test.mjs`) rather than
introducing a new test framework. Minimum cases:

- Happy path: valid `record` call appends exactly one TSV row with the
  correct computed `iter`, and one JSONL event.
- Concurrent calls: two `record` invocations fired near-simultaneously
  produce two distinct, sequential `iter` values and two well-formed TSV
  rows (no interleaved/corrupted line).
- Rejected verdict, out-of-range score, missing synthesis file, and
  synthesis path outside the allowed root each fail closed with exit 2 and
  **no** file mutation (verify via before/after file hash or mtime).
- Index-regen failure (simulate by pointing at a broken/missing Python
  script path) still leaves the TSV row and JSONL event written, exits
  non-zero, and prints the `index-stale` warning.
- `logs/autoloop.jsonl` and its parent dir are created from scratch when
  absent (this is the real, current state on this machine — do not assume
  the file pre-exists in tests).

## Explicitly out of scope for this CLI

- Writing the synthesis note itself.
- Self-scoring / verdict decision logic — the caller supplies `--verdict`
  and `--score` already decided.
- Promoting a staged skill-pack to `~/.coven/skills/` or a familiar's own
  `skills/` dir — that's Val's `coven-review` gate, per the skill's
  sibling-skill interface section.
- Any mutation of `SOUL.md`, `IDENTITY.md`, or `MEMORY.md` — the skill
  contract forbids this explicitly, and this CLI has no reason to touch
  those paths at all.
